# Host `src/SVNAssist.Host` (net472, in-proc)

Package VSSDK classico (`AsyncPackage`) con due tool window ("SVN Changes", "SVN Log") che ospitano la UI web in WebView2, un relay verso `SVNAssist.Backend.exe` (StreamJsonRpc su stdio) e i comandi `.vsct`. Contratto: `src/Shared/RpcContract.cs`.

## Build
```
dotnet publish src/SVNAssist.Backend -c Release -o src/SVNAssist.Backend/bin/publish   # framework-dependent
dotnet restore src/SVNAssist.Host
msbuild src/SVNAssist.Host/SVNAssist.Host.csproj -p:Configuration=Release              # -> bin/Release/net472/SVNAssist.vsix
```
- Il VSIX contiene `ui/` (= `src/SVNAssist.UI.Web` senza `contract/`) e `backend/` (= `BackendPublishDir`, default `src/SVNAssist.Backend/bin/publish`; si cambia con `-p:BackendPublishDir=C:\dir\`). Senza backend la build avvisa e il VSIX non lo contiene.
- Con il MSBuild di VS 18 senza `MSBuild.exe.config` usare il launcher `tools/msb.cs` (compilarlo con `csc`: esegue MSBuild in un AppDomain con la config presa dal template; vedi `webview2-spike.md`). La versione del manifest deve coincidere con `Directory.Build.props` (la build fallisce se no).
- Test in VS: installare il `.vsix` in un'istanza sperimentale (`VSIXInstaller /rootSuffix:...`), poi `devenv /rootsuffix ... /updateconfiguration`. Log dell'host: `%LOCALAPPDATA%\SVNAssist\host-log.txt`. I comandi hanno nome (`SVNAssist.Changes`, `SVNAssist.Log`, ...).

## Comportamento
- Il backend parte alla prima vista/comando (non all'avvio di VS), muore con VS (Job Object KILL_ON_JOB_CLOSE), si riavvia se cade (max 4/min) e l'host rimanda `ready` di ogni vista, `SolutionChangedAsync`, `ThemeChangedAsync` e l'evento `backendRestarted`.
- Relay: pagina -> `IBackend.DispatchAsync(view, json)` (solo `ready` e `cmd`); backend -> `IHost.PushAsync(view, json)`. Il backend deve coalescere gli `state` (~16 ms), l'host non lo fa. Se il backend non risponde l'host manda `reply ok:false` / toast.
- Tema: `ThemeBridge` manda `theme{kind,vars}` al `ready`, a `VSColorTheme.ThemeChanged`, a cambio `windowTheme`; solo le variabili derivabili da VS (sfondi, testi, bordi, selezione, link, font): colori di stato/diff/sintassi restano quelli di `tokens.css` per il `kind`. Alto contrasto: colori di sistema.
- Impostazioni: Tools > Options > SVNAssist (chiavi camelCase del contratto; `GetSettingsAsync` ritorna anche gli alias minuscoli della 0.1.0). Le API key sono cifrate con DPAPI nel registro.
- **Log come documento**: `LogToolWindow` e' registrata con `ProvideToolWindow(Style = VsDockStyle.MDI, Transient = true)`: `ShowToolWindowAsync` la apre come tab nell'area editor (grande, come i diff) e non viene ripristinata al riavvio di VS. E' un'unica istanza: un nuovo percorso ne aggiorna titolo (`Pane.Caption = "Log: <cartella o file>"`) e contenuto invece di aprire tab separati (scelta piu' semplice e affidabile con una WebView2 per finestra).
- `IHost.ShowLogAsync(path)` apre il documento Log col titolo del percorso e inoltra `logLoad{path}`.
- `IHost.ShowFolderDiffAsync(path)` mostra la finestra Log e inoltra `logFolder{path}` (elenco dei file modificati della cartella; clic = diff nativo). `OpenDiffAsync` (`IVsDifferenceService.OpenComparisonWindow2`) apre ogni diff: file della working copy (BASE ↔ working copy), file di una revisione (`r-1 ↔ r`) e confronto tra due revisioni, con file temporanei in `%TEMP%\SVNAssist\diff` (esportati con `svn export -r`, cancellati alla chiusura del backend, quelli orfani dopo un giorno). TortoiseSVN non e' mai necessario.
- Menu: Extensions > SVNAssist (Changes, Commit..., Update, Update to revision..., Switch..., Merge..., Cleanup, Log). In Solution Explorer solo **Show Log** (`CmdSeLog`, gruppo `GroupSe` su `IDM_VS_CTXT_ITEMNODE/PROJNODE/FOLDERNODE`, `DefaultInvisible`+`DynamicVisibility`: visibile solo con un elemento selezionato dentro una working copy, cercando `.svn` risalendo le cartelle; manda `RunPathCommandAsync("log", [path])`, il backend apre il Log sul solo file anche per .csproj). Accanto c'e' **SVN Add** (`CmdSeAdd`, stesso gruppo): visibile solo se TUTTI gli elementi selezionati (anche multipli, `IVsMultiItemSelect`) risultano non versionati nella cache dello stato di `SvnSccService.IsUnversioned` (provider spento o cache vuota = nascosta); manda `RunPathCommandAsync("add", paths)` (stesso comando del backend, `svn add --force --parents`, conferma per le cartelle, errori in dialogo) e il refresh aggiorna icone e finestra Changes. Il resto del menu SVN e' stato rimosso (ridondante con Changes). Menu contestuale dell'editor di codice: **SVN: Revert Selected Changes** (`CmdRevertSel`, anche nel pannello destro del diff, che e' il file di lavoro vero); **Next/Previous Change in Diff** (`CmdNextChange/CmdPrevChange`, Alt+F8 / Shift+Alt+F8 globali con `editor="guidVSStd97"`; Ctrl+Alt+Giu'/Su' e' di VS, `Window.ShowEzMDIFileList`; anche nel menu contestuale del codice e in Extensions) non passano da nomi di comandi VS: prendono la vista attiva (`IVsTextManager.GetActiveView` → `IVsEditorAdaptersFactoryService.GetWpfTextView`); se `IWpfDifferenceViewerFactoryService.TryGetViewerForTextView` trova un diff usano `IDifferenceViewer.ScrollToNext/PreviousChange(wrap: true)` (sposta il cursore nel pannello attivo), altrimenti chiedono al backend i blocchi del `svn diff` (`IBackend.GetChangedBlocksAsync(file)`, stesso parser di `LineRevert`) e `DiffNav.Next/Previous` (`src/Shared/DiffNav.cs`, logica pura con giro) sceglie la riga. Poi `EnsureSpanVisible(AlwaysCenter)`. **Scorciatoie personalizzabili**: Tools > Options > SVNAssist > Scorciatoie (`NextChangeShortcut`, `PreviousChangeShortcut`, default Alt+F8 / Shift+Alt+F8); `SVNAssistPackage.ApplyShortcuts` le applica all'avvio e a ogni OK delle Options con EnvDTE `Command.Bindings = ["Global::<tasti>"]` sui comandi `SVNAssist.NextChange/PreviousChange`; vuoto = nessuna scorciatoia, valore non valido = riga nel log e binding invariato.
- **Pulsante annulla nel diff**: `RevertMargin` (MEF, `IWpfTextViewMarginProvider` sul margine sinistro del solo pannello destro: ruoli `DifferenceViewerRoles.RightViewTextViewRole`/`Ubiquitous...`; asset `MefComponent` nel `.vsixmanifest`). Verifica 0.2.0: asset MefComponent e catalogo MEF corretti, nessun errore di composizione in `ComponentModelCache\*.err`, costanti dei ruoli giuste (`RIGHTDIFF`, `UBIRIGHTDIFF`); causa esatta del pulsante mancante NON confermata senza una prova in VS: ora ruoli larghi (anche `DIFF`, `UBIDIFF`, `DOCUMENT`, `EDITABLE`; il filtro e' in `Refresh`), margine `Collapsed` finche' la vista non risulta RightView di un diff, riprova su `Loaded` e `ApplicationIdle` (il viewer si registra nel servizio dopo la creazione delle viste) e una riga `RevertMargin: attivo...` nel log di SVNAssist quando si attiva. Un `Button` con `CrispImage(KnownMonikers.Undo)` per ogni `Difference` di `DifferenceBuffer.CurrentSnapshotDifference.LineDifferences`, riposizionato a ogni `LayoutChanged`/`SnapshotDifferenceChanged`; il clic chiama `SVNAssistPackage.RevertRangeAsync(file, da, a, doc)` (salva, poi `revertlines`). Esito di `revertlines`: solo toast in Changes, nessun dialogo. "Update" del menu Extensions invia il cmd `update` alla vista `changes`.

## Aggiunte al contratto (rispetto alla prima versione)
- `IBackend.ThemeChangedAsync(string kind)`.
- **SVN Switch**: nessun metodo RPC nuovo. Il comando `.vsct` `CmdSwitch` (0x0107, Extensions > SVNAssist > Switch...) invia `cmd switchOpen` alla vista `changes` (come Update to revision); selettore, svn e conferme stanno nel backend (comandi `switchOpen|switchRefresh|switchCancel|switchOk` in `docs/ui-protocol.md`). Nuova impostazione `repoLayout` (Tools > Options > SVNAssist > Generale), passata con `GetSettingsAsync`.
- **SVN Merge**: il comando `.vsct` `CmdMerge` (0x0108, Extensions > SVNAssist > Merge...) invia `cmd mergeOpen` alla vista `changes` (come Switch); la scelta della sorgente, svn, i conflitti e "Annulla merge" stanno nel backend. Metodo RPC nuovo **`IHost.ShowLogWindowAsync(title)`**: apre il Log come documento con quel titolo (`Pane.Caption`) **senza** inoltrare `logLoad`; lo usa il backend per "Merge da branches/x" (il contenuto del Log in modalita' merge lo ha gia' impostato lui) e per tornare a "Log: cartella" con Chiudi merge. Comandi e snapshot in `docs/ui-protocol.md` ("Log: modalita' merge").
- **Conflitti**: metodo RPC nuovo **`IHost.ShowChangesWindowAsync()`** (porta in primo piano SVN Changes: dopo un merge/update/switch con conflitti (senza dialogo) e dal pulsante "Risolvi i conflitti" del Log). L'editor di merge a 3 vie lo avvia il backend (non serve l'host): `vsDiffMerge.exe` del VS ospite (variabile `VSAPPIDDIR`, ereditata dal backend) o di un'installazione sotto `Program Files\Microsoft Visual Studio\<versione>\<edizione>\Common7\IDE\CommonExtensions\Microsoft\TeamFoundation\Team Explorer` (prima "18", poi 2022, 2019), altrimenti `TortoiseMerge.exe`, altrimenti il file con i marcatori in VS (`OpenFileAsync`). Argomenti di vsDiffMerge: `theirs mine base merged /m`.
- `IHost.PromptTextAsync(message, label, default)`: dialogo con un campo di testo (revisione, messaggio di lock); `null` se annullato. `IHost.PromptCredentialsAsync(detail, defaultUser)`: dialogo utente/password (password mascherata, "Ricorda" attivo di default) → `[utente, password, "1"|"0"]` o `null`; mostrato solo dopo un errore di autenticazione di svn, mai loggato.
- `IBackend.RunPathCommandAsync(string command, string[] paths)`: comandi su percorsi (`update|add|revert|diff|ignore|log|commit|updaterev|cleanup|lock|unlock`; non piu' collegati a menu: il menu di Solution Explorer e' stato tolto) e **`revertlines`**, usato da "SVN: Revert Selected Changes": `paths = [file, "da-a"]` (righe 1-based del file di lavoro). L'host prende file e selezione dalla vista di testo attiva (`IVsTextManager.GetActiveView`), salva il documento se modificato e il backend (`LineRevert`) calcola dal `svn diff` quali blocchi toccano le righe, li riporta a BASE preservando encoding/BOM/fine riga e riscrive il file (VS lo ricarica; niente Ctrl+Z). Messaggio "Annullate N righe" e refresh di Changes.

## Stato SVN in Solution Explorer (0.4.0, provider SCC)
- `SvnSccService` (`SvnSccService.cs`) e' un provider di source control di VS (`ProvideSourceControlProvider` + `ProvideService`; `IVsSccProvider` + `IVsSccManager2`), solo per i **glifi**: nessun comando. Il package lo attiva con `IVsRegisterScciProvider.RegisterSourceControlProvider` all'apertura di una solution dentro una working copy (cartella `.svn` risalendo dal .sln, nessuna chiamata svn) e lo disattiva (GUID nullo) alla chiusura o con l'opzione spenta. Opzione: Tools > Options > SVNAssist > Generale > "Mostra lo stato SVN in Solution Explorer" (`ShowSccGlyphs`, default attiva).
- Stato: `IBackend.GetSccStatesAsync()` (percorso -> nome `SvnStatusKind`, dalla cache di Changes; avvia il caricamento anche senza finestre) e `IHost.SccStatusChangedAsync()` (il backend lo chiama a ogni lettura di `svn status`, anche dal watcher). L'host coalesce 300 ms, aggiorna la cache e chiama `IVsSccProject2.SccGlyphChanged(0,...)` su tutti i progetti caricati (i progetti SDK-style non chiamano `RegisterSccProject` dopo l'attivazione, quindi si scorre `IVsSolution.GetProjectEnum`). `GetSccGlyph` legge solo la cache. File non in cache dentro la working copy = normale.
- Mappa stato->glifo in `src/Shared/SccGlyph.cs` (testata): icone **standard** VsStateIcon (normale CHECKEDIN, modificato/sostituito CHECKEDOUT, aggiunto EDITABLE, non versionato ORPHANED, conflitto DISABLED, eliminato/mancante READONLY). Provato in VS 18: la shell NON ha richiesto `IVsSccGlyphs` (icone custom come il "?" di Git): da indagare se si vuole l'aspetto Git. I file ignorati non sono nell'elenco di svn status e appaiono come normali.
